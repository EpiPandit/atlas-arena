# AtlasArena web app

A Next.js 14 site (pages router) exported as static files (`output: 'export'`)
and served from S3 behind CloudFront. UI is Chakra UI v3; the explore map is
MapLibre GL with a deck.gl overlay that reads Cloud Optimized GeoTIFFs directly.

## Development

Requirements: Node 22 (see [`.nvmrc`](.nvmrc)) and Yarn 4, the version pinned in
`package.json`'s `packageManager` field (enable it with `corepack enable`).

```shell
nvm install
corepack enable
yarn
yarn dev        # http://localhost:3000
```

Other scripts:

- `yarn build`: static export to `out/`
- `yarn lint`: ESLint (`next/core-web-vitals`); the build ignores lint errors
- `yarn format` / `yarn format:fix`: Prettier

### Environment

Every variable is optional; the defaults are in `src/config/constants/general.js`.
Copy [`.env.example`](.env.example) to `.env.local` to override them:

- `NEXT_PUBLIC_ATLASARENA_API_URL`: the `atlasarena-model-infra` API (sign-in,
  custom model runs). Set it to an empty value to hide sign-in.
- `NEXT_PUBLIC_ATLASARENA_JOBS_URL`: public outputs of finished model runs.
- `NEXT_PUBLIC_ATLASARENA_DATA_URL`: the shared data bucket, holding the FOI
  parameters CSV used by the Run Models tab (`data/FOI/`) and the explore
  page's COGs (`cogs/`).

They are inlined at build time, so a change needs a rebuild.

The backend has two environments, **dev** and **prod**, and each has its own
API and jobs bucket. The first two variables must always come from the same
one. The data bucket is shared by both. The defaults point at dev, which is
what local development uses; the deploy workflow sets the values for staging
(dev) and production (prod) from repository variables (see
[Deploying](#deploying)).

## How it fits together

```text
src/
├── pages/                 index, explore, about, methodology, resources
├── components/
│   ├── explore/           map, sidebar, layers, legend, Run Models panel
│   ├── home/ about/       page sections
│   └── custom/ ui/        shared form controls, Chakra provider, toaster
├── config/
│   ├── catalog.json       every map layer (see below)
│   ├── features.json      labels and groups for model feature codes
│   ├── constants/         page text, URLs, colours
│   └── md/ styles/        Markdown rendering and Chakra theme
├── libs/                  catalog, API client, jobs, run history, URL hash, CSV
└── store/                 app context (filter options) and auth
```

### Layer catalog

`src/config/catalog.json` lists every layer the explore page can show:

- `viruses`, `species`, `time_frames`, `models`, `variables`: display names,
  colours and value ranges, keyed by stable ids used in the URL.
- `layers`: one entry per COG, as `{ virus, species, time_frame, model,
  variable, path }`. `path` is relative to `cogs/` in the shared data bucket
  (`COGS_URL` in `src/config/constants/general.js`). Set `"enabled": false` to
  hide one.
- `defaults`: what the explore page shows on first load.

Most of it (the SDM and FOI layers for 78 species) is generated by
`scripts/build_default_layers.py` in `atlasarena-model-infra`; the original
Junin, Machupo and Guanarito layers come from `../data_preparation`. Edit by
hand only for small fixes, since a regeneration overwrites everything except
`defaults`.

`libs/catalog.js` flattens the catalog into rows, and `store/actions.js` derives
the sidebar's virus, species, time frame and model options from them.

### Map rendering

- `components/explore/DeckOverlay.jsx` mounts deck.gl on the `react-map-gl`
  MapLibre map through `@deck.gl/mapbox`'s `MapboxOverlay`, which works with
  MapLibre too (no Mapbox account or token). It passes
  `deviceProps: { _reuseDevices: true }` so React Strict Mode's double mount
  reuses the WebGL device.
- `components/explore/cogLayer.js` builds a `COGLayer` from
  `@developmentseed/deck.gl-geotiff`. The rasters are float32, which the
  library's default pipeline doesn't handle, so it has its own
  `getTileData`/`renderTile`: an `r32float` texture, a nodata/threshold discard,
  a linear rescale to the variable's range, and a colormap from `MAP_COLORS`.
- Stay on `maplibre-gl` 5.x. Version 6 loads its worker relative to
  `import.meta.url`, which Next's webpack build breaks.

### Custom model runs

Signed-in users (Google, through the API's OAuth flow; `store/auth.jsx`) can
upload presence points for one species in the Run Models panel. `libs/jobs.js`
submits the job, `components/explore/useCustomJob.js` polls it, and the finished
rasters load from `NEXT_PUBLIC_ATLASARENA_JOBS_URL` like any other layer. Job ids are remembered
per account in `localStorage` (`libs/runHistory.js`), since the API cannot
list a user's jobs. The selected layer and open job are kept in the URL hash
(`libs/hashParams.js`), so a view can be shared by link.

## Content

The home, about, methodology and resources pages are rendered at build time
from Markdown in `public/markdown`, read with `gray-matter` in `libs/markdown.js`.
Short UI strings live in `src/config/constants/`.

Each file has front matter with a mandatory `name` and `layout`, and optional
`kicker`, `title` and `sub_title`. Pages either load one file by name, or load
every file and pick by `layout`, so a new file with an existing layout shows
up without code changes:

- `page`: loaded by name (`home.md`, `about.md`, `resources.md`)
- `methodology`: loaded by name (`methodology.md`)
- `virus`: a virus write-up with a `species` list; shown on the home page, the
  resources page and the explore page's "about" panel
- `specie`: a reservoir species write-up; home and resources pages
- `publications`: a publication entry; resources page

```text
---
name: Junin virus
species:
  - Calomys musculinus
  - Calomys laucha
layout: virus
---

# Junin virus
...
```

Images go in `public/markdown/images` and are referenced relatively, as
`![alt](images/file.png)`; the loader rewrites the path.

## Deploying

`.github/workflows/deploy.yaml` builds the site, syncs `out/` to the site's S3
bucket and invalidates CloudFront:

| Push to   | Deploys    | Built against                        |
| --------- | ---------- | ------------------------------------ |
| `staging` | staging    | dev backend (`AtlasArenaDevStack`)   |
| `main`    | production | prod backend (`AtlasArenaProdStack`) |

It reads these repository settings (Settings > Secrets and variables >
Actions). The run fails before building if one it needs is missing.

| Name                                 | Kind     | Used for                         |
| ------------------------------------ | -------- | -------------------------------- |
| `AWS_ACCESS_KEY_ID`                  | secret   | both sites                       |
| `AWS_SECRET_ACCESS_KEY`              | secret   | both sites                       |
| `ARENA_S3_BUCKET`                    | secret   | production site bucket           |
| `CLOUDFRONT_DISTRIBUTION_ID`         | secret   | production distribution          |
| `ATLASARENA_API_URL`                 | variable | production: prod `ApiUrl`        |
| `ATLASARENA_JOBS_URL`                | variable | production: prod `JobsPublicUrl` |
| `ATLASARENA_DATA_URL`                | variable | production: `DataPublicUrl`      |
| `STAGING_ATLASARENA_API_URL`         | variable | staging: dev `ApiUrl`            |
| `STAGING_ATLASARENA_JOBS_URL`        | variable | staging: dev `JobsPublicUrl`     |
| `STAGING_ATLASARENA_DATA_URL`        | variable | staging: `DataPublicUrl`         |
| `STAGING_ARENA_S3_BUCKET`            | variable | staging site bucket              |
| `STAGING_CLOUDFRONT_DISTRIBUTION_ID` | variable | staging distribution             |

The URLs are CloudFormation outputs of the `atlasarena-model-infra` stacks and
must end in `/`.

`deploy-staging.sh` does the staging deploy by hand, if it is ever needed. It
takes AWS credentials, `STAGING_BUCKET` and `STAGING_DISTRIBUTION_ID`, and
builds with the code defaults, which are the dev backend.

For Google sign-in to work on a new origin, add it to `allowed_return_origins`
for that environment in `atlasarena-model-infra`'s `infra/app.py` and redeploy
the stack.
